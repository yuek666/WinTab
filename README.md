# WindowTabManager

Windows 原生系統匣程式，接管 **Alt+Tab** 與 **Win+Tab**，提供視窗即時預覽、依螢幕切換、邏輯群組、三套組態，以及兩個切換清單各自的隱藏設定。

使用 C#、WinForms、.NET Framework 4.8 與 Win32 API。正式執行會列出並操作真實 Windows 視窗；沒有背景截圖、虛擬桌面管理或開機自動啟動功能。

**交付狀態：已可建置並執行；原生 API 與自動測試已部分實測。實體 Alt/Win 按鍵、使用者觸發的焦點切換與螢幕拔除，仍須依 `TESTING.md` 人工驗證。** 不應將已安裝 Hook 解讀為已驗證所有 Shell 快捷鍵行為。

## 建置與啟動

適用目標：Windows 10/11 x64、.NET Framework 4.8。這次實測環境為 Windows 11 build 26200、.NET Framework 4.8.1；Windows 10、ARM64 與混合 DPI 尚未實測。

在專案目錄執行：

```powershell
.\build.ps1
.\bin\WindowTabManager.exe
```

也可以直接雙擊 `bin\WindowTabManager.exe`。啟動後只顯示系統匣圖示，若圖示被 Windows 收進溢位區，請點工作列右下角的上箭頭。左鍵開啟控制面板，右鍵提供組態切換、暫停／恢復及退出。

程式、系統匣及控制面板使用提供的藍色視窗 SVG 圖示，原始檔在 `assets/WindowTabManager.svg`；多尺寸 ICO（16–256px）已內嵌於執行檔。若修改 SVG，可執行 `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\Build-Icon.ps1` 重建圖示，再建置程式。

執行中的 exe 會被 Windows 鎖定。需要保留舊版工作階段時，可使用 `.\build.ps1 -OutputDirectory bin-icon` 另建新版；從舊版系統匣退出並處理未儲存修改後，再啟動新版。

`build.ps1` 使用 Windows 已安裝的 `Framework64\v4.0.30319\csc.exe`，無 NuGet 套件、無下載步驟，不需要 .NET SDK。有 Visual Studio／MSBuild 和 4.8 targeting pack 時，也可開啟 `WindowTabManager.csproj` 建置。若 PowerShell 執行原則阻擋本地腳本，可針對此程序執行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1
```

## 操作

### 遊戲／無邊框全螢幕相容性修訂

本次修訂已建置為 `bin-gamefix\WindowTabManager.exe`。先從舊版系統匣退出、處理未儲存修改，再啟動此檔；不需再次建置。若自行修改程式，可用 `.\build.ps1 -Test -OutputDirectory bin-gamefix` 建置。設定與原版共用。

修訂內容：Hook 依收到的左右 Alt／Win／Shift／Ctrl 事件追蹤修飾鍵，Alt 另參考事件的 `LLKHF_ALTDOWN`；啟動及工作階段解鎖時重新讀取狀態。每次開啟預覽面板（包括重開同一個 Win 總覽）都以 `SetWindowPos(HWND_TOPMOST)` 重新指定置頂順序；Alt 面板保留不主動取得焦點的設計。

使用者回報 GRYPHLINE 啟動器的《明日方舟》在視窗全螢幕下無法觸發。**尚未在該遊戲實測，以上是通用補強，不能保證已解決該遊戲問題。** 普通無邊框置頂測試視窗不等同於遊戲或獨佔全螢幕。

若仍無反應：

1. 在遊戲中分別按 Alt+Tab、Win+Tab，記下時間；切回桌面，從系統匣開「快捷鍵診斷」，Ctrl+A、Ctrl+C 複製結果。資訊只保留本次執行最近一次 Alt／Win 開啟請求，沒有一般按鍵紀錄或背景寫入檔案。
2. 如果該次時間未出現，代表沒有開啟請求到達 UI；先在遊戲啟動後「暫停」再「恢復接管」重測。其他 Hook 先攔截、Win 鍵鎖、權限或注入事件等都有可能，需要進一步區分。
3. 若時間更新，但沒有面板，請比較一般視窗與無邊框全螢幕；診斷的 `Visible=True` 與置頂成功僅是 API／視窗狀態，不證明遊戲畫面沒有遮住它。
4. 若診斷顯示遊戲來源為系統管理員而本程式是一般權限，可先退出本程式，再右鍵 exe「以系統管理員身分執行」作比較。這不代表能處理所有遊戲的攔截；程式不會自行要求提高權限。

參考：[鍵盤 Hook 的非同步狀態時序](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/ms644985(v=vs.85))、[遊戲可過濾 Windows 鍵](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/disabling-shortcut-keys-in-games)、[SetWindowPos 的置頂行為](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)。這些 API 限制不代表已證實該遊戲採用特定攔截方式。

Ctrl+Alt+Tab、其他 Win 快捷鍵、一般 Tab 會放行。這版略過注入的鍵盤事件，故透過其他工具的 `SendInput`、遠端桌面或鍵盤重映射觸發的組合鍵不保證會接管。

控制面板的「Alt+Tab 依作用中視窗判定螢幕」未勾選時，使用滑鼠所在螢幕（預設）；勾選時使用作用中視窗。螢幕歸屬採 `MonitorFromWindow` 的最大相交面積規則；最小化視窗使用還原前位置。沒有相交時選最近螢幕。

在同一次 Alt 操作中，不因游標移動、新視窗或視窗順序更新而更換候選清單。已關閉的候選在選取時會被拒絕；螢幕設定變動會取消正在顯示的切換面板，並要求更新清單。

## 分組與三套組態

沒有有效啟動預設時，第一次收到視窗清單就依應用程式建立初始群組。之後出現且無匹配規則的新視窗放入「未分組」。可再次使用「套用應用程式分組」重建群組，或直接新增／重新命名／刪除群組，將視窗移入選定群組。

群組可以包含多個螢幕的視窗，與 Windows 虛擬桌面無關。刪除群組只將視窗移至未分組，不會關閉視窗。控制面板及 Win+Tab 總覽共用同一個工作區，編輯立即生效。

Win+Tab 是切換用的預覽覆蓋層，沒有程式標題列、工作列按鈕或組態管理表格。組態／全域設定請從系統匣開啟控制面板；總覽只保留與當下分組、切換有關的操作。大量視窗可用滾輪瀏覽。

固定的三個**儲存欄位**各自包含完整群組集合，群組數量不限於三個。

1. 選擇欄位，按「命名並儲存／更新」，在對話框確認組態名稱。
2. 按「載入」載入選定欄位；空白欄位載入空的分組工作區。
3. 「設為啟動預設」只允許已儲存欄位；「清除啟動預設」恢復啟動時的應用程式分組。
4. 手動編輯不會修改已儲存快照。只有明確執行儲存，才更新指定欄位。
5. 載入、重新套用預設分組或退出時，有未儲存修改會提供「儲存至選定欄位」「捨棄並繼續」「取消」。儲存失敗或取消命名時，不會繼續切換。

初始自動分組也屬於本次尚未儲存的工作區，因此退出時可能出現儲存提示。

## 視窗匹配規則

組態保存的是 **完整程式路徑 + 視窗類別 + 當時標題 + 群組 ID**，不保存 HWND 或 PID。

- 路徑比較不區分大小寫；視窗類別及標題使用精確比較。
- 同一程式／類別有多個視窗時，只有「唯一的相同標題」和「唯一的儲存規則」互相對應才套用。
- 若整個程式／類別只有一個現存視窗與一條規則，允許標題變更後還原。
- 標題相同的多視窗、衝突規則、或多視窗且標題變動，不猜測對應，保留未分組／預設顯示，請手動編輯。
- 同次執行且視窗身分維持不變時，標題變更不會清除既有手動分組或隱藏設定。
- 無法讀取程式路徑的視窗可在本次操作，但不跨次匹配；例如某些受保護或不同權限的程序。
- 不存在的視窗略過；再次儲存時，保留已載入但目前不存在的規則。程式不會自行啟動它們。
- 同一程式多個完全相同標題無法穩定跨次辨識，亦不依 HWND 或列舉順序硬配。已判為不明確的本次視窗可透過重新載入組態再匹配，或直接手動指定。
- 程式路徑（例如版本目錄）改變會使規則失配。應重新指定後儲存。

「唯一候選」只能確定當下沒有競爭候選，不能證明它一定是同一份文件；需要文件級別精準還原的多視窗情境，應保留穩定且不同的標題。

## 隱藏與全域設定

Alt+Tab 和 Win+Tab 隱藏設定相互獨立。隱藏只排除本程式的切換清單，控制面板仍保留該視窗；不呼叫隱藏實際視窗的 API、不關閉程式，也不會改變原生 Alt+Tab 的內容。

螢幕判定模式、隱藏規則、啟動預設欄位是全域設定，變更後立即嘗試保存；切換組態不覆寫它們。隱藏規則使用上面的保守匹配方式。

預設設定位置：

```text
%LOCALAPPDATA%\WindowTabManager\settings.json
```

寫入採同目錄暫存檔與原子取代，上一版保留為 `settings.json.bak`。檔案損壞或不支援時拒絕啟動，不會默默以空組態覆寫；可退出後複製 `.bak` 取代損壞檔案。無法寫入時會顯示錯誤，保留本次記憶體修改。

測試隔離資料可使用：

```powershell
.\bin\WindowTabManager.exe --data-dir .\artifacts\sandbox-profile
```

同一資料目錄限定單一執行個體。不要同時以不同資料目錄啟動多個接管程序，避免 Hook 互相競爭。

## 原生限制與效能策略

- 列舉目前桌面上可見、有標題、非工具／no-activate、非 DWM-cloaked 的頂層應用視窗；一般 owned 視窗會排除，明確 `WS_EX_APPWINDOW` 例外。這是本程式定義的可管理集合，並非 Windows Shell 的完整 Task View 私有邏輯。
- 不列出其他虛擬桌面被 cloaked 的視窗，不處理 UAC 安全桌面、鎖定畫面或登入畫面。
- `SetForegroundWindow` 有作業系統限制；程式先還原，再嘗試帶到前景，拒絕時以系統匣通知回報。不修改 foreground-lock 系統設定、不注入其他程序、不強制繞過安全限制。
- 快捷鍵使用獨立訊息迴圈的 `WH_KEYBOARD_LL`，只處理快捷鍵狀態與投遞命令。Win／Alt 選單抑制採短暫 Ctrl 事件，若被 UIPI 拒絕會回報。不同權限程序、全螢幕遊戲、Shell 更新、其他 Hook 工具需實機測試。
- Microsoft 說明低階 Hook 超時可能被靜默移除。本程式避免在回呼中列舉、讀圖示或存檔；如果發現原生切換突然恢復，可在系統匣暫停再恢復以重新註冊。沒有宣稱可偵測所有靜默移除情況。
- 視窗事件更新採 300ms 合併處理，閒置約每 5.1 秒補查，避免每次事件都完整列舉。MRU 自啟動後的前景事件開始記錄；第一次快照其餘視窗以列舉 Z 順序作初始順序。
- 圖示只在面板需要時讀取，最多四個背景工作，每個 WM_GETICON 呼叫最多等待 25ms，結果快取並移除已關閉視窗的項目。面板關閉後不再提出新的圖示請求，已開始的有限工作可完成。
- Alt+Tab 和 Win+Tab 以 `DwmRegisterThumbnail`／`DwmUpdateThumbnailProperties` 建立真正的 DWM 即時預覽，保持來源長寬比，不擷取位圖、不設預覽更新計時器。來源畫面由 Windows 合成器更新。
- 只註冊目前可見卡片的縮圖；捲動離開、隱藏視窗、關閉面板、切換至控制面板或退出時，會解除對應的 DWM 註冊。待機時不保留縮圖。
- 最小化視窗可能顯示最後的畫面，或暫時沒有內容；受保護、特殊繪圖或不同權限視窗可能黑畫面。API 拒絕時會顯示「無法取得視窗預覽」，仍可點卡片嘗試切換。程式不為了預覽而還原／啟動來源程式。
- 沒有背景畫面擷取或動畫。效能數字是這台機器的短時量測，不是固定承諾；DWM／GPU 額外負擔不包含在本程序 CPU 數字內。見 `TESTING.md`。

```powershell
.\verify.ps1 -Preview

```

原生測試會短暫建立自己的視窗、嘗試取得前景與移動滑鼠，再還原原滑鼠位置。效能測試會執行真實接管約 45 秒，期間開啟 Win+Tab 即時預覽，再自動結束；請勿同時執行正式程式。UI 渲染測試使用範例資料，不安裝鍵盤 Hook；`-Preview` 另外建立兩個真實來源視窗驗證 DWM 註冊、更新與釋放。一般 `DrawToBitmap` 圖片不包含 DWM 合成的像素，不能把 UI 圖片當成即時預覽內容的視覺驗證。

自動測試 exit code 0 代表沒有斷言失敗，**不代表 `BLOCKED` 項目已驗證**。完整結果、驗收清單與 Windows 文件來源見 `TESTING.md`。
